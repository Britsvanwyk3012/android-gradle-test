# Buy & Sell App — Contact Number/Label Investigation
## Prepared for independent review (Fred/Dog and Claude)

**Baseline inspected:** V12.13 Test 23 corrected source
**Proposed package:** V12.14 Test 24 changes, repackaged as Test 25 for traceability
**Date:** 18 September 2026

## User reproduction

1. Edit a phone number's label and save: Google and Android phone show the changed label correctly.
2. Delete the number and save: number disappears from Google and Android phone.
3. Deselect and reselect the client card: warning reports the deleted number as existing, with label `Custom`.
4. `Add to B&S`: number is added locally but with `Custom`.
5. `Add as new number`: B&S shows `New`, while Google/phone show `Custom`.
6. Replace number: replacement popup and automatic save work correctly.
7. Ignore: returns to the card with a green button; repeated deselect/reselect does not show another warning.

## Confirmed faults

### F1 — `New` becomes `Custom` in Google/Android Contacts
**Evidence:** `googlePhoneType()` mapped `"new"` to `"custom"`.
**Cause confidence:** Confirmed by source inspection.
**Fix applied:** `New` is now passed as the custom Google label string `New` rather than being converted to `custom`.
**Expected outcome:** A B&S label of `New` should no longer be forcibly converted to `Custom`. Device presentation should be re-tested because Android/Google may display custom labels differently by client/version.

### F2 — Duplicate normalized numbers collapse during Google sync
**Evidence:** Google sync builds a `linkedMapOf` keyed by `normalizePhone(number)`, so two entries with the same normalized number but different labels can only produce one output entry. The later entry overwrites the earlier entry.
**Cause confidence:** Confirmed by source inspection.
**Fix applied:** Edit save now rejects duplicate normalized numbers with a clear message. External-number actions also refuse to add a number already present locally.
**Expected outcome:** B&S will no longer save ambiguous duplicate copies of the same number for one client. This is a deliberate data-integrity rule; if the business requires duplicate numbers with different labels, that policy must be redesigned rather than silently collapsing entries.

### F3 — Deleted number still triggers the warning
**Evidence:** User cannot find the number in Google or Android Contacts, yet reselecting the card triggers the warning.
**Cause confidence:** Not confirmed. The warning receives a `PhoneContact` snapshot passed through the selection flow. The code also performs Google/Android synchronization asynchronously. A stale snapshot, cached list, or timing issue remains possible.
**Fix status:** Not fully fixed in this package. The correct next step is to force a fresh contact-provider read before duplicate detection and log the source/number being evaluated. The app must not treat a stale in-memory contact snapshot as proof that a number currently exists.

### F4 — `Custom` is propagated by the warning actions
**Evidence:** The warning uses `detected.label` and the source contact parser maps Android `TYPE_CUSTOM` to its custom label, or to `Custom` when the raw label is blank. The current Google mapping also converted `New` to `custom`.
**Cause confidence:** Partly confirmed. The `New` conversion is confirmed; the exact origin of the warning's `Custom` value needs runtime logging after F3 is addressed.
**Fix applied:** Corrected `New` mapping. Runtime verification remains required.

## Proposed next fixes

1. Before `detectExternalPhoneChanges`, reload the selected contact from Android Contacts Provider using its contact ID; do not rely on the card's old `PhoneContact` object.
2. Compare the fresh contact list to the latest local B&S phone JSON.
3. Add diagnostic logging (number hash/normalized key, contact ID, source, label, local record contents, and timestamp) without logging full personal phone numbers in user-facing screens.
4. Ensure Google deletion completion is acknowledged before refreshing the contact list or evaluating external changes.
5. Keep duplicate detection based on normalized numbers, but show a user-readable conflict instead of silently overwriting a label.
6. After every Google update, re-read the contact and verify both number set and label/type values. Google `updateContact` replaces fields named in the update mask, so the current person and ETag must be used.

## Independent review questions

- Is rejecting duplicate normalized numbers the correct business rule, or should duplicate numbers be permitted with a deterministic label policy?
- Does Google People API preserve a custom type such as `New`, or should the app map the internal placeholder `New` to a standard type such as `mobile`?
- Should the warning be renamed from “number exists” to “number detected in current phone contact snapshot” until a fresh read is completed?
- Is Ignore intended to suppress the same number only for the current app session, or persistently?
- Is the green button after Ignore correctly scoped to the client and normalized number?
